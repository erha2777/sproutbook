# 植物养护管理应用 — 需求分析与技术方案

> 状态：v0.1 草案（历史文档，保留作为设计决策的记录；实现现状以 README 与 CHANGELOG 为准）
> 目标平台：Windows 桌面优先 → 后续 Android / iOS
> UI 风格参考：像素风农场经营游戏（当时的参考图已清理，仓库内不含任何第三方游戏素材）

---

## 1. 结论速览

| 项 | 结论 |
|---|---|
| 整体可行性 | **可行**。这是一个「本地数据库 + CRUD + 规则引擎 + AI 增强」的典型桌面应用，没有技术上的死路。 |
| 最大风险 | 不在代码，而在 **① 数据模型（可编辑模板）② 养护计划的知识正确性 ③ 美术资源版权**。 |
| 最大的结构性问题 | 需求把「植物物种百科信息」和「我养的这株植物」混成了一个实体，**必须先拆成两层**。 |
| 最该推迟的功能 | 第 5 条「星露谷式植物生长展现」——它是惊喜功能，不是实用功能，且美术成本远高于代码成本。 |
| 最该补的功能 | **环境档案（位置/气候/光照）+ 天气霜冻预警**。它比生长动画价值高一个数量级，且几乎零成本（Open-Meteo 免费无 Key）。 |
| 最该砍掉的做法 | 用 AI 直接生成全年养护日历。**必须改成「规则库生成 + AI 补规则/解释」**。 |

## 2. 逐条功能可行性评级

| # | 需求 | 可行性 | 难度 | 主要坑 |
|---|---|---|---|---|
| 1 | 信息模板 / 手动录入 | ✅ 高 | 中 | 可编辑模板 = 动态字段，查询与迁移会变复杂 |
| 1a | AI 自动补全信息 | ✅ 高 | 低 | 幻觉，尤其**毒性/科属**；必须有人工确认环节 |
| 1b | 识图生成 | ⚠️ 中 | 中 | 通用视觉模型细粒度识别准确率有限，只能给「候选」不能给「结论」 |
| 2 | 列表 / 搜索 / 统计 / 分类 | ✅ 高 | 低 | 中文全文搜索需要 trigram 分词器 |
| 3 | 配方（配土/肥料） | ✅ 高 | 低 | 容易被做成「备注框」，要有引用关系才有价值 |
| 4 | 养护计划（手动/AI 生成 + 提醒） | ⚠️ 中 | **高** | 知识正确性、气候适配、应用关闭后的提醒 |
| 5 | 星露谷式生长展现 | ⚠️ 中 | 中高 | **美术资源版权**；任意物种的生长阶段素材无法穷举 |
| 6 | AI API Key / 模型配置 | ✅ 高 | 低 | 密钥必须进系统钥匙串，绝不能进 git |
| 7 | 上传 GitHub / 健壮稳定 | ✅ 高 | 中 | 未签名安装包会被 SmartScreen/Gatekeeper 拦截；数据库迁移必须有 |

## 3. 三个必须先解决的结构性问题

### 3.1 【最重要】物种库 与 我的植株 必须分成两层

需求里「植物名称、科、毒、耐寒」是**物种级知识**（百科、可共享、AI 可补全），而「播种日期、放在哪个阳台、现在什么状态」是**实例级数据**（私有、唯一）。

现在混在一起会导致：

- 养 3 盆月季 → 月季的「科/毒/耐寒」被抄 3 遍，改一次要改 3 处，AI 也要调用 3 次；
- 养护规则无法挂在物种上；
- 统计「我养了几个科」要做去重脏活；
- 无法做「物种包」分享（社区功能没了）。

**修正模型：**

```
species（物种库 / 知识层）  ← 1 : N →  plants（我的植株 / 实例层） → environments（环境档案）
```

- AI 补全、识图、百科信息 → 全部写入 `species`；
- 养护计划、照片、生长日志 → 全部挂在 `plants`；
- 用户可以「选已有物种」或「新建物种」。

### 3.2 环境档案要成为一等公民（需求里缺失）

`environments` 表：南向阳台 / 北窗台 / 露台 / 地栽，含`光照等级、实际直射小时数、城市经纬度、气候区、是否可加温/防冻`。

有了它才能做到：

- 养护计划按**你实际的环境**调整，而不是给全中国一份通用日历；
- **光照匹配度**提示：「这株要全日照，你放的是北窗台（2h 直射）」；
- **霜冻预警**：接入 Open-Meteo（免费、无需 Key），`明晚最低 -3℃，你有 4 盆耐寒区不足的植物在室外`。

这一条比「生长动画」有用得多，强烈建议进第一版。

### 3.3 模板系统是数据模型的根，必须最先做

「可以编辑模板，用以新增信息」——这句话决定了整个应用的架构。三种实现方式：

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 动态 `ALTER TABLE` 加列 | 查询最快 | 迁移地狱、字段删不掉、无法回滚 | ❌ |
| 纯 EAV（一行一属性） | 最灵活 | 查询拼装复杂、性能随字段数下降 | ❌ |
| **JSON 列 + 索引投影表** | 灵活 + 可索引 + 易迁移 | 需维护投影一致性 | ✅ **推荐** |

**具体做法：**

- `field_definitions` 定义字段（key / 标签 / 分组 / 类型 / 单位 / 选项 / 排序 / 是否必填）；
- `species.attributes_json` 、`plants.attributes_json` 存实际值；
- `attr_index(owner_id, field_key, value_text, value_num, value_date)` 作为**投影表**，用于筛选、排序、统计；投影可随时从 JSON 全量重建（一条 SQL 就能自愈）。

**字段类型至少要支持这些**（否则后期会痛）：

`text` `longtext` `number(+unit)` `month_range`（花期/开花时期）`hours_range`（光照时长）`select` `multiselect` `bool` `tags` `date` `image` `link`

**关键点：结构化 > 自由文本。**

- ❌ 「花期：春季」→ ✅ 月份区间 `3-5 月`（否则日历、统计、提醒全都用不了）
- ❌ 「耐寒：较耐寒」→ ✅ 最低耐受温度 `-15℃` + 耐寒区（可参与霜冻预警）
- ❌ 「毒：有毒」→ ✅ 等级 + **部位 + 症状 + 急救** 结构字段

**模板演进的安全规则（健壮性核心）：**

1. 字段**只归档，不物理删除**（`archived_at`）；
2. 字段 key 不可改（改 key = 数据丢失）；
3. 每次 schema 变更走 `schema_migrations` 版本表，**迁移前自动备份数据库**；
4. 模板变更后提供「数据体检」：列出被影响的植株数。

## 4. 技术选型

### 4.1 候选对比（考虑到「先桌面、后手机」）

| 方案 | 桌面体验 | 复用到手机 | 像素风 UI | 包体积 | 结论 |
|---|---|---|---|---|---|
| **Tauri 2 + React + TS** | 好 | ✅ **官方支持 Android/iOS** | 好（就是 Web） | ~10 MB | ✅ **首选** |
| Electron + React + TS | 最好 | ❌ 不能，需另起 Capacitor 壳 | 好 | ~150 MB | 🟡 备选（不想碰 Rust 时） |
| Flutter + Flame | 好 | ✅ 真正一套代码 | 中（像素风要自己搭） | ~30 MB | 🟡 若生长动画是核心卖点 |
| Godot 4 | 差（表单 CRUD 很痛苦） | ✅ | **最好** | ~50 MB | ❌ 80% 的功能在和引擎打架 |
| 纯 Web / PWA | 中（不像「桌面应用」） | ✅ 天然 | 好 | 0 | 🟡 最快验证想法 |

### 4.2 推荐栈

```
Tauri 2 (Rust 壳)  +  React 18 + TypeScript + Vite
      ↓
SQLite (rusqlite / sqlx, WAL 模式, 单写入者)
      ↓
Zustand（轻量状态） + TanStack Query（数据层）
      ↓
Tailwind CSS + CSS 变量主题（像素风）+ pixelated 渲染
      ↓
打包：tauri-action → GitHub Releases（Windows / macOS / Linux）
```

**为什么是 Tauri 2：** 它的移动端是官方一等公民，前端代码 100% 可复用 —— 这正好匹配「先桌面、后手机」的路线，不需要重写。包体积和内存占用也远优于 Electron。参考 [Tauri 2.0 stable](https://tauri.app/blog/)、[CLI v2.9](https://tauri.app/release/@tauri-apps/cli/v2.9.0/)。

**唯一代价**：需要 Rust 工具链，移动端要额外装 Android SDK/NDK 与 Xcode。如果这让你犹豫，就用 Electron —— 但请把业务逻辑写成 **框架无关的纯 TS `core` 包**，这样将来换壳或上 Capacitor 都不用重写。

**从第一天就做的事（现在便宜，以后昂贵）：**
把所有领域逻辑（模板、校验、规则引擎、AI 解析）放进 `packages/core`，**零 DOM、零 Node API、零框架依赖**，UI 只做展示。这是「桌面 → 手机」能否低成本迁移的唯一决定因素。

## 5. 数据模型草案（SQLite DDL）

```sql
PRAGMA journal_mode = WAL;
PRAGMA foreign_keys = ON;

-- 0. 迁移版本
CREATE TABLE schema_migrations (
  version    INTEGER PRIMARY KEY,
  name       TEXT NOT NULL,
  applied_at TEXT NOT NULL DEFAULT (datetime('now'))
);

-- 1. 设置（绝不含 API Key，密钥进系统钥匙串）
CREATE TABLE settings (key TEXT PRIMARY KEY, value TEXT NOT NULL);

-- 2. 环境档案
CREATE TABLE environments (
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL,                 -- 南向阳台 / 北窗台 / 露台 / 地栽
  kind TEXT NOT NULL,                 -- indoor|balcony|terrace|ground|greenhouse
  light_level TEXT,                   -- full_sun|part_shade|shade
  light_hours REAL,                   -- 实际直射小时
  climate_zone TEXT, province TEXT, city TEXT,
  lat REAL, lon REAL,                 -- 天气/霜冻预警用
  can_heat INTEGER NOT NULL DEFAULT 0,
  frost_protected INTEGER NOT NULL DEFAULT 0,
  sort_order INTEGER NOT NULL DEFAULT 0,
  archived_at TEXT
);

-- 3. 模板字段定义
CREATE TABLE field_definitions (
  id INTEGER PRIMARY KEY,
  key TEXT NOT NULL UNIQUE,
  label TEXT NOT NULL, label_en TEXT,
  group_name TEXT,                    -- 基础/形态/习性/养护/安全
  type TEXT NOT NULL,                 -- text|longtext|number|month_range|hours_range|
                                      -- select|multiselect|bool|tags|date|image|link
  unit TEXT,
  options_json TEXT, default_json TEXT,
  is_required INTEGER NOT NULL DEFAULT 0,
  is_system   INTEGER NOT NULL DEFAULT 0,   -- 系统字段不可删
  sort_order  INTEGER NOT NULL DEFAULT 0,
  archived_at TEXT                          -- 只归档，不物理删除
);

-- 4. 物种库（知识层，可共享、可 AI 补全）
CREATE TABLE species (
  id INTEGER PRIMARY KEY,
  scientific_name TEXT,                       -- 拉丁学名
  family TEXT, genus TEXT,                    -- 科 / 属（建议做候选词，不要纯自由文本）
  attributes_json TEXT NOT NULL DEFAULT '{}',
  source TEXT,                                -- manual|ai|imported|seed
  confidence_json TEXT,                       -- 逐字段 AI 置信度
  verified_at TEXT,                           -- 人工确认时间
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at TEXT NOT NULL DEFAULT (datetime('now'))
);
CREATE INDEX idx_species_family ON species(family);
CREATE INDEX idx_species_sci    ON species(scientific_name);

-- 5. 我的植株（实例层）
CREATE TABLE plants (
  id INTEGER PRIMARY KEY,
  species_id INTEGER REFERENCES species(id) ON DELETE SET NULL,
  nickname TEXT NOT NULL,                     -- 「阳台那盆月季」
  env_id INTEGER REFERENCES environments(id) ON DELETE SET NULL,
  status TEXT NOT NULL DEFAULT 'growing',     -- growing|dormant|sick|dead|gifted
  acquired_at TEXT,                           -- 入手/播种日期（生长动画的时间基准）
  pot_size TEXT,
  substrate_recipe_id INTEGER,
  attributes_json TEXT NOT NULL DEFAULT '{}', -- 实例级覆盖值
  notes TEXT, cover_image_id INTEGER,
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at TEXT NOT NULL DEFAULT (datetime('now')),
  archived_at TEXT
);
CREATE INDEX idx_plants_species ON plants(species_id);

-- 6. 属性索引投影（可从 JSON 全量重建）
CREATE TABLE attr_index (
  owner_kind TEXT NOT NULL,        -- species|plant
  owner_id   INTEGER NOT NULL,
  field_key  TEXT NOT NULL,
  value_text TEXT, value_num REAL, value_date TEXT,
  PRIMARY KEY (owner_kind, owner_id, field_key)
) WITHOUT ROWID;
CREATE INDEX idx_attr_text ON attr_index(field_key, value_text);
CREATE INDEX idx_attr_num  ON attr_index(field_key, value_num);

-- 7. 中文全文检索（trigram 分词，CJK 子串搜索可用）
CREATE VIRTUAL TABLE plant_fts USING fts5(
  nickname, aliases, scientific_name, notes,
  tokenize='trigram'
);

-- 8. 图片（DB 只存相对路径，文件放 appdata，不进 git、不进 DB）
CREATE TABLE images (
  id INTEGER PRIMARY KEY,
  plant_id INTEGER REFERENCES plants(id) ON DELETE CASCADE,
  species_id INTEGER REFERENCES species(id) ON DELETE SET NULL,
  task_id INTEGER,
  path TEXT NOT NULL, thumb_path TEXT,
  width INTEGER, height INTEGER,
  caption TEXT, taken_at TEXT,
  origin TEXT,                                -- user|ai|web
  sort_order INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
);

-- 9. 材料与配方
CREATE TABLE materials (
  id INTEGER PRIMARY KEY, name TEXT NOT NULL UNIQUE,
  kind TEXT NOT NULL,                         -- substrate|fertilizer|amendment|pesticide|pot
  unit TEXT, note TEXT
);
CREATE TABLE recipes (
  id INTEGER PRIMARY KEY, name TEXT NOT NULL,
  kind TEXT NOT NULL,                         -- 配土|肥料|药剂
  note TEXT,
  created_at TEXT NOT NULL DEFAULT (datetime('now')), archived_at TEXT
);
CREATE TABLE recipe_items (
  id INTEGER PRIMARY KEY,
  recipe_id INTEGER NOT NULL REFERENCES recipes(id) ON DELETE CASCADE,
  material_id INTEGER NOT NULL REFERENCES materials(id),
  ratio_part REAL,                            -- 5:3:2 的「份」
  amount REAL, unit TEXT, note TEXT,          -- 或绝对用量
  sort_order INTEGER NOT NULL DEFAULT 0
);

-- 10. 养护计划与任务
CREATE TABLE care_plans (
  id INTEGER PRIMARY KEY,
  plant_id INTEGER REFERENCES plants(id) ON DELETE CASCADE,
  name TEXT NOT NULL, year INTEGER,
  source TEXT NOT NULL,                       -- manual|rule_engine|ai
  climate_snapshot_json TEXT,                 -- 生成时环境快照，可复现/重算
  rule_version TEXT, prompt_version TEXT,
  status TEXT NOT NULL DEFAULT 'active',
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at TEXT NOT NULL DEFAULT (datetime('now'))
);
CREATE TABLE care_tasks (
  id INTEGER PRIMARY KEY,
  plan_id INTEGER REFERENCES care_plans(id) ON DELETE CASCADE,
  plant_id INTEGER REFERENCES plants(id) ON DELETE CASCADE,
  action_type TEXT NOT NULL,                  -- water|fertilize|prune|repot|pest|frost_protect|sow|harvest|observe
  title TEXT NOT NULL, detail TEXT,
  due_date TEXT NOT NULL,                     -- YYYY-MM-DD
  window_days INTEGER NOT NULL DEFAULT 3,     -- 允许提前/延后天数
  recurrence TEXT,                            -- {"freq":"day","interval":7,"until":"..."}
  priority INTEGER NOT NULL DEFAULT 2,
  status TEXT NOT NULL DEFAULT 'pending',     -- pending|done|skipped|expired
  completed_at TEXT, completed_note TEXT,
  source TEXT NOT NULL DEFAULT 'manual',
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
);
CREATE INDEX idx_task_due   ON care_tasks(status, due_date);
CREATE INDEX idx_task_plant ON care_tasks(plant_id, due_date);

-- 11. 物种养护规则库（先有规则，AI 只用来补规则）
CREATE TABLE care_rules (
  id INTEGER PRIMARY KEY,
  species_key TEXT NOT NULL,                  -- 学名或属级通配 'Rosa*'
  hemisphere TEXT NOT NULL DEFAULT 'N',       -- 南北半球
  climate_zone TEXT,                          -- NULL = 通用
  month_from INTEGER NOT NULL, month_to INTEGER,
  action_type TEXT NOT NULL,
  title TEXT NOT NULL, detail TEXT,
  priority INTEGER NOT NULL DEFAULT 2,
  source TEXT NOT NULL,                       -- seed|ai|user
  verified INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
);
CREATE INDEX idx_rule_lookup ON care_rules(species_key, hemisphere, month_from);

-- 12. AI 调用审计（调试、复现、成本统计）
CREATE TABLE ai_runs (
  id INTEGER PRIMARY KEY,
  kind TEXT NOT NULL,                         -- fill_fields|id_image|gen_plan|gen_rule|chat
  provider TEXT, model TEXT, base_url TEXT, prompt_version TEXT,
  input_json TEXT, output_json TEXT,
  status TEXT NOT NULL, error TEXT,
  prompt_tokens INTEGER, completion_tokens INTEGER, duration_ms INTEGER,
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
);

-- 13. 养护日志（时间线 / 生长动画的数据源）
CREATE TABLE care_logs (
  id INTEGER PRIMARY KEY,
  plant_id INTEGER NOT NULL REFERENCES plants(id) ON DELETE CASCADE,
  task_id INTEGER, log_date TEXT NOT NULL,
  kind TEXT NOT NULL,                         -- water|fertilize|photo|symptom|note|repot
  content TEXT, image_id INTEGER,
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
);
```

## 6. AI 能力边界与落地方案

### 6.1 三条铁律

1. **无 AI 也必须完整可用。** AI 是增强，不是依赖。没配 Key 的用户要能用全部功能。这是健壮性的第一原则。
2. **AI 永不直接写库。** 一律产出「草稿」，Diff 预览后由用户确认落库，逐字段可勾选、可改。落库时记录 `source` 与 `confidence`。
3. **安全字段永不自动确认。** `毒`（等级/部位/症状/急救）与 `科属`必须标记为「待核实」，UI 显著提示，直到用户手动确认。这条不是洁癖 —— 误食有毒植物的代价是真实的。

### 6.2 结构化输出

用 JSON Schema / tool-calling 约束输出，而不是让模型写自由文本再正则抠。解析器要有 `prompt_version`，老草稿能被新版本安全处理（解析失败 → 保留原始文本 + 提示重新生成，绝不崩）。

### 6.3 「识图生成」要降低预期

通用视觉模型在**细粒度物种识别**上并不可靠，品种级更差；专用模型（Flora Incognita、Pl@ntNet 一类）在真实拍摄条件下也多是「属/科级可信、种级待定」。参考文献：[FloraLens 属/科识别评估](https://www.dcc.fc.up.pt/~edrdo/publications/papers/floralens.pdf)、[瑞士生物多样性监测中的自动植物识别评估](https://www.sciencedirect.com/science/article/pii/S1574954125003255)。

**因此产品形态应该是：**

```
拍照 → 给出 Top-3 候选（学名 + 置信度 + 依据特征）
     → 引导用户补充「拍摄地区 / 季节 / 株型」提高准确率
     → 用户选定 → 生成信息草稿 → 确认入库
```

而不是「拍一下就自动填好」。另外把识别做成**可插拔 Provider**（视觉大模型 / Pl@ntNet / 本地模型），用户可换。

### 6.4 AI 设置的工程要求

- **一个「OpenAI 兼容 + Base URL」抽象覆盖 95% 场景**：OpenAI、DeepSeek、Moonshot、智谱、OpenRouter、Ollama、LM Studio、各类中转网关全部通吃；Anthropic / Gemini 作为可选适配器。
- **对话模型与视觉模型分开配置**（很多人是「文本模型 + 另一个视觉模型」）。
- **密钥存系统钥匙串**（Tauri stronghold / keyring crate；Electron `safeStorage`）。配置文件只存 provider / model / baseURL。开发环境用 `.env` 且必须在 `.gitignore` 里。
- 必备：流式输出、超时与指数退避重试、**可取消**、并发上限、token 与预估费用显示、连接测试按钮。
- 所有调用写 `ai_runs` 审计表 —— 出问题时你能知道「它当时到底收到了什么」。

## 7. 养护计划引擎（全项目最难的部分）

### 7.1 为什么不能「让 AI 生成全年计划」

- 输出不确定 → 用户没法「只改一条」而不重生成；
- 无法验证 → 错的知识你也不知道；
- 无法离线 → 没 Key 就没功能；
- 无法积累 → 同一物种被反复重新生成，规则永远不成体系。

### 7.2 正确架构：规则库驱动 + AI 辅助

```
输入：species 的 care_rules + environment（气候区/光照/室内外/盆栽地栽）+ plants.acquired_at + 半球
  ↓ 规则引擎（纯函数、可单测、可复现）
输出：带日期的 care_tasks 列表（可编辑、可勾选完成）
  ↓ 可选
AI 只负责三件事：
  ① 为规则库里没有的物种「生成规则草稿」（人工确认后入库，沉淀下来）
  ② 把任务列表解释成人话（「为什么这周要修剪」）
  ③ 针对单株的临时问答（「叶子发黄怎么办」）
```

两条路径最终都落到**同一个可编辑的 `care_tasks` 模型**，用户视角一致。

### 7.3 关键设计点

- **气候区 + 半球 + 室内外**必须参与计算（`climate_snapshot_json` 存快照，便于「重算」）。南半球用户月历要翻转 —— GitHub 开源后必然会有海外用户。
- **时间窗**：园艺不是精确到日的。任务带 `window_days`（±3 天），UI 显示「本周内」而不是「10 月 14 日必须做」。这比精确日期更符合现实，也更不容易让用户焦虑。
- **周期任务**：浇水/施肥用 `recurrence` JSON（每天/每周/每 N 天/每月）。不要引入完整 RFC5545 库，简单的几种就覆盖 95%。
- **提醒的现实**：应用关闭时的系统通知，桌面端是真实成本。分阶段做：
  - v1：启动时「补算错过 + 今日待办」+ 系统托盘常驻 + 可选开机自启；
  - v2：注册 Windows 计划任务 / macOS LaunchAgent；
  - 移动端：真推送（这也是移动版存在的最大理由之一）。
- **月历视图**是它的天然 UI，而且**像素风月历会非常好看** —— 这是风格与功能结合得最好的地方，建议把美术预算优先投在这里而不是生长动画。
- **导出**：把月历导出成图片/PDF 贴在冰箱上。低成本、高口碑。

## 8. 星露谷风格 UI 与「生长展现」

### 8.1 ⚠️ 版权风险（上传 GitHub 前必须处理）

- **不要使用从游戏里提取的素材**（贴图、音效、字体）。公开发布会构成侵权。
- **不要用「星露谷物语」相关名称做应用名或仓库名** —— 那是商标。
- 应用名、Logo、图标、像素素材都必须是原创或明确许可的。

**可用素材来源（务必逐个核对许可并记入 `CREDITS.md`）：**

- 优先选 **CC0 / Public Domain**：Kenney、OpenGameArt 的 CC0 分区；
- LimeZu 等作者的像素包：**逐包确认**，不少是「可商用但不可再分发素材本身」，而 GitHub 开源仓库恰恰就是再分发 → 这类不能直接放进仓库；
- 最保险：**自己画或委托画**，少量核心素材 + 程序化配色（色相偏移）扩展。

### 8.2 生长展现的正确做法

难点不是代码，是**「任意用户录入的物种都要有生长阶段素材」**这个不可能穷举的需求。

**解法：通用原型 × 阶段，而不是每物种一套图。**

```
株型原型：草本 / 灌木 / 乔木 / 藤本 / 多肉 / 球根  （6 种）
生长阶段：种子 / 萌芽 / 营养生长 / 花苞 / 盛花 / 结果 / 落叶休眠  （6-7 阶段）
→ 约 36-42 张素材即可覆盖全部物种
```

再叠加：色相/尺寸程序化变化 + 允许用户为某阶段上传自己的照片覆盖。这样既可控又有惊喜感。

### 8.3 技术实现与「真实感」

- **先做简单方案**：CSS Grid + `image-rendering: pixelated` 的静态「我的花园」视图。个人花园只有几十株，DOM 完全够用。
- 只有需要大量精灵、粒子、天气动画时才上 **PixiJS / Canvas**。不要一开始就上引擎。
- **让它与现实绑定才有价值**：当前阶段由 `播种日期 + 物种花期 + 当前月份 + 是否休眠` 推导 → 打开应用看到的是「**我的花园现在这个月的样子**」，而不是装饰动画。
- 隐藏彩蛋：一键导出「花园卡片」图片便于分享 —— 这是开源项目最好的传播素材。

**结论：这是 v2 功能，不是 v1。但数据模型（`acquired_at`、`status`、`care_logs`）必须在 v1 就设计好，否则后期补不上。**

### 8.4 两个像素风必备的工程细节

1. **整数倍缩放**：像素素材只按 ×1/×2/×3 缩放 + `image-rendering: pixelated`，否则在 150% 缩放屏上会糊（这是这类应用最常见的可见 bug）。必须在 100%/125%/150%/4K 下都测。
2. **像素字体**：中文字体是难点。像素中文矢量字体（如「Fusion Pixel 缝合像素字体」）可解决，**注意确认其授权（OFL 类可用）并记入 CREDITS**；或者中文用普通无衬线体、仅装饰元素用像素风 —— 后者更省事也更易读。

## 9. 健壮性与 GitHub 发布清单

### 9.1 数据安全（对数据类应用 = 生命线）

- SQLite **WAL 模式 + 单写入者 + 事务**；用「杀掉进程」的方式测崩溃恢复。
- **启动时自动滚动备份**数据库（保留最近 N 份），迁移前强制备份。
- **导入 / 导出**：全量 JSON 导出导入 + CSV 导出 + 一键打开数据目录。
- **图片不进数据库**（不要 base64），存 appdata 目录、DB 只存相对路径，并生成缩略图供列表使用。

### 9.2 绝不能提交到仓库

`API Key` / `settings.db`（含个人数据）/ 用户上传的照片 / `node_modules` / `target` / 构建产物 / `.env`

### 9.3 发布流水线

- GitHub Actions 矩阵构建（windows / macOS / linux）→ 自动发 Release（Tauri 用 `tauri-action`）。
- **未签名安装包的拦截必须写进 README**：Windows SmartScreen 提示、macOS Gatekeeper「已损坏」。给出用户可操作步骤（右键打开 / `xattr -dr com.apple.quarantine`）。这是最常见的差评来源，说清楚就能避免。
- 自动更新（Tauri updater）可选，但需要签名密钥与公开端点，建议 v1 之后再说。
- 仓库必备：`README.md`（中英双语）、`LICENSE`（代码 MIT/Apache-2.0；美术素材单独声明）、`CREDITS.md`、`CHANGELOG.md`、`CONTRIBUTING.md`、`SECURITY.md`（漏洞与密钥泄露报告路径）。

### 9.4 国际化与本地化（现在做便宜，以后做很贵）

- `i18n` 从第一天做（zh-CN / en）；
- **单位制**（公制/英制）与**南北半球**是 i18n 的表亲，一并进 `settings`。

### 9.5 测试策略（只测纯逻辑，不追覆盖率）

- 规则引擎：给定物种 + 环境 + 日期 → 期望任务列表（**黄金文件测试**）；
- 迁移：空库 → 最新版；老版本库 → 最新版，数据不丢；
- AI 响应解析：正常 / 残缺 JSON / 多字段缺失 / 超长，都不能崩；
- 模板变更：删字段、改类型后，旧数据仍可读。

## 11. 明确建议推迟 / 砍掉的东西

| 项 | 建议 |
|---|---|
| 星露谷式生长展现 | **推迟到 v1.0**，但 v0.1 就保留 `acquired_at` / `care_logs` 字段 |
| 用 AI 生成整份养护日历 | **砍掉**，改为规则引擎 + AI 补规则 |
| 识图「自动填全信息」 | **降级**为 Top-3 候选 + 人工确认 |
| 自建通用表单引擎 / 可视化模板设计器 | **砍掉**，字段定义用「分组 + 排序 + 类型」的表单式 UI 就够 |
| 云同步 / 账号体系 | **砍掉**，本地优先；开源项目加后端 = 长期运维负担 |
| 完整 RFC5545 重复规则 | **砍掉**，几种简单周期足够 |

## 12. 建议补充的功能（性价比高）

1. **霜冻/极端天气预警**（Open-Meteo 免费无 Key）—— 静态的「耐寒」字段瞬间变成行动。
2. **光照匹配度提示** —— 用「环境光照 vs 物种需求」算契合度。
3. **智能合集 / 保存筛选**：「本月开花」「需要春化的」「有毒且儿童可触及」「待核实毒性」。
4. **养护月历导出图片/PDF** —— 可贴在冰箱上。
5. **植株时间线**：照片 + 日志的纵向对比，满足「记录养护过程」的心理需求，成本远低于动画。
6. **待核实清单**：集中展示所有 AI 填充但未人工确认的字段，形成信任闭环。

## 13. 命名建议（避免商标风险）

需要一个原创名字，例如：`Sproutbook` / `Gardenstead` / `苔历 Mossday` / `一畦` / `Bloomplot`。
（仓库名、应用名、图标都应与「星露谷物语/Stardew」无关。）
